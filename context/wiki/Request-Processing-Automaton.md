# Request Processing Automaton

## Назначение

**Request Processing Automaton** — внешний операционный автомат подготовки
HTTP-запроса. Он координирует потоковый парсер Вирта и чистый Марковский
переписыватель URI, но сам не владеет сокетом.

```text
handleClient
    │ recv Input Chunk
    ▼
Request Processing Automaton
    ├── Wirth Parser
    └── Markov URI Rewriter
    │
    ▼
Prepared Request
```

`handleClient` владеет соединением, повторяет `recv`, хранит возвращённое
состояние автомата и исполняет следующий сетевой шаг.

## Контракт шага

Концептуально один шаг имеет форму:

```text
oldState + new Input Chunk
            ↓
newState + processing result
```

Результат различает:

```text
NeedMoreData
Ready
Error
```

- `NeedMoreData` требует сохранить новое состояние и прочитать следующий chunk;
- `Ready` содержит подготовленное представление запроса;
- `Error` передаёт причину обработчику, который применяет политику отказа.

## Фазы

Первая модель содержит следующие фазы:

```text
Parsing
Rewriting
Ready
Failed
```

1. `Parsing`: новый фрагмент передаётся Вирту. Его фаза, абсолютный индекс и
   найденные границы сохраняются между вызовами.
2. `Rewriting`: после обнаружения границ URI исходный URI передаётся Маркову.
3. `Ready`: Марков вернул новый URI, а автомат подготовил результат для
   обработчика.
4. `Failed`: разбор завершился ошибкой или превышен лимит.

`Rewriting` может оказаться не наблюдаемой runtime-фазой, а одним чистым
переходом. Это следует решить после определения точного Haskell-контракта.

## Память автомата

На первом этапе автомат хранит единое логическое представление:

```text
Request Memory
    ├── Accumulated Buffer
    ├── Offset Table
    └── Wirth State
```

**Accumulated Buffer** содержит все полученные байты до завершения подготовки
запроса. Это позволяет позднее использовать request line, заголовки и уже
полученную часть тела.

**Offset Table** дополняется по мере разбора и содержит полуоткрытые границы:

```text
uriStart
uriEnd
headersEnd
bodyStart
```

URI представлен диапазоном `[uriStart, uriEnd)`. Границы относятся к одному
логическому буферу независимо от того, на сколько Input Chunk был разделён
запрос.

Логически буфер один, однако его физическая реализация остаётся открытым
вопросом. Последовательное `buffer <> chunk` для строгого `ByteString` может
повторно копировать накопленные данные. Кандидаты для отдельного эксперимента:

- заранее выделенный буфер с проверяемым верхним лимитом;
- рост ёмкости крупными блоками;
- последовательность chunks с однократной материализацией;
- другой специализированный накопитель.

Приоритет — минимальный измеренный overhead. Формулировка «zero overhead»
остаётся целью, а не доказанным свойством до анализа Core и измерения
аллокаций.

## Внутренние автоматы

### Wirth Parser

Вирт получает сохранённое состояние и только новый, ранее не обработанный
фрагмент. Он возвращает обновлённое состояние и дополняет Offset Table. Сокет,
накопление буфера и Марков находятся вне его ответственности.

### Markov URI Rewriter

Марков запускается после появления `uriStart` и `uriEnd`:

```text
original URI → Markov rules → rewritten URI
```

Он только преобразует URI. Марков не маршрутизирует запрос и не принимает
сетевых решений.

## Результат подготовки

После завершения автомат возвращает обработчику:

```text
Accumulated Buffer
Offset Table
Rewritten URI
```

Полный изменённый запрос заранее не реконструируется. По границам он может быть
представлен как:

```text
Prefix | Rewritten URI | Suffix
```

`Suffix` может уже содержать часть тела. Дальнейшая отправка этих сегментов и
последующих body chunks относится к отдельному автомату пересылки.

## Обязательные сценарии проверки

- URI целиком находится в одном chunk;
- URI разделён между двумя или несколькими chunks;
- `\r\n\r\n` разделён в каждой возможной позиции;
- chunk с концом заголовков содержит часть тела;
- chunk заканчивается точно на `headersEnd`;
- вход оборван до завершения заголовков;
- malformed input и превышение лимита приводят к `Error`;
- Вирт ни при одном сценарии не получает ранее обработанные байты повторно.

## Открытые решения

1. Физическое представление растущего Accumulated Buffer.
2. Лимиты request line, заголовков и общего удерживаемого объёма.
3. Точная форма Offset Table и обязательность отдельных границ.
4. Является ли `Rewriting` состоянием или чистым переходом.
5. Контракт передачи результата автомату пересылки.
