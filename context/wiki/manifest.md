# Application-Specialized Proxy

## Основной тезис

**Build the proxy, don’t configure the proxy.**

Проект не ставит целью создание ещё одного универсального reverse proxy, который затем конфигурируется под произвольное приложение.

Вместо этого предполагается построение **специализированного прикладного proxy-автомата** из:

* набора общих proxy-примитивов;
* модели конкретного приложения;
* его операций;
* правил маршрутизации;
* политик авторизации;
* необходимых преобразований данных.

Универсальность находится в **наборе примитивов и механизме построения**, а не в каждом получившемся runtime.

Конкретный proxy должен содержать только ту функциональность, которая необходима конкретному приложению.

---

## Application-aware L7 proxy

Proxy рассматривается не только как инфраструктурный компонент перед приложением, но как часть прикладной архитектуры.

Он может знать достаточно о протоколе и модели приложения, чтобы принимать решения на уровне L7:

* распознавать прикладную операцию;
* маршрутизировать запрос;
* применять политики доступа;
* извлекать необходимые признаки из данных;
* выполнять преобразования;
* выбирать backend.

При этом proxy не должен становиться копией бизнес-логики приложения.

Он должен знать **минимально необходимую информацию для принятия конкретного решения**.

---

## От REST к операции

REST path не всегда достаточно хорошо выражает семантику действия.

Например:

```text
PATCH /documents/42
```

показывает ресурс и HTTP-операцию, но не обязательно содержит информацию, необходимую для принятия решения об авторизации.

Поэтому внутри proxy запрос может быть приведён к более явному прикладному представлению, близкому к RPC:

```text
Call
  subject
  operation
  target
  context
```

HTTP, REST или другой протокол при этом могут оставаться внешним транспортом.

Proxy получает возможность работать не с синтаксисом URI как таковым, а с **прикладной операцией**.

---

## Policy specialization

Политика авторизации не обязательно должна интерпретироваться proxy в полном виде во время выполнения.

Предполагается исследовать возможность компиляции policy заранее в некоторое компактное представление, достаточное для принятия решения.

Концептуально:

```text
Application Policy
        +
Application Model
        ↓
Specialization
        ↓
Authorization Representation
        ↓
Proxy Runtime
```

Proxy должен различать только те состояния приложения, которые способны изменить результат решения.

Если два различных прикладных состояния приводят к одному и тому же решению policy, для proxy они могут быть эквивалентны.

Это открывает возможность исследовать **минимальное информационное представление**, необходимое для авторизации.

---

## Selective streaming parsing

Если решение зависит только от нескольких атрибутов большого сообщения, нет необходимости материализовывать всё сообщение как объект.

Например, для большого JSON body:

```text
byte stream
    ↓
streaming parser
    ↓
required fields only
    ↓
features
    ↓
policy decision
```

Policy потенциально может определять не только способ принятия решения, но и **какую информацию вообще необходимо извлечь из входного потока**.

Таким образом, ненужная для решения информация не обязана:

* полностью парситься;
* аллоцироваться;
* храниться в памяти.

---

## Общая модель

В первом приближении архитектуру можно выразить так:

```text
Proxy Primitives
        +
Application Model
        +
Operations / Policies / Rules
        ↓
Specialization / Build
        ↓
Application-Specific Proxy Automaton
        ↓
Runtime
```

Получившийся runtime может быть значительно уже универсального proxy.

Один экземпляр может содержать только маршрутизацию.

Другой:

* маршрутизацию;
* authorization;
* streaming parsing.

Третий дополнительно может выполнять прикладные преобразования протокола.

---

## Принцип минимальности

Специализированный proxy не должен знать всё приложение.

Его задача — различать **ровно столько прикладных состояний, сколько необходимо для выполнения возложенных на него операций**.

Поэтому размер и сложность конкретного proxy должны определяться не общей функциональностью платформы, а сложностью конкретного приложения и его политик.

---

## Направление исследования

На текущем этапе это архитектурная гипотеза, а не окончательный дизайн.

Необходимо экспериментально исследовать:

* минимальный набор proxy-примитивов;
* форму описания приложения;
* представление прикладной операции;
* способы специализации policy;
* минимальное кодирование authorization state;
* потоковое извлечение необходимых признаков;
* границу между proxy и бизнес-логикой приложения;
* возможность построения proxy как явного автомата.

Реализация должна развиваться постепенно из конкретных работающих экспериментов.

---

## Ключевая формула

> **Build the proxy, don’t configure the proxy.**

Не настраивать универсальную машину под приложение.

**Строить новую прикладную proxy-машину из примитивов и знания о конкретном приложении.**
