# Project Glossary

Этот глоссарий фиксирует канонические термины проекта. Английское имя термина
сохраняется намеренно: оно может использоваться в ADR, Issues, документации и
коде. Наличие термина в глоссарии само по себе не требует немедленно создавать
одноимённый Haskell-тип.

## Соглашения

- При первом существенном употреблении термина в новом Issue или ADR его по
  возможности выделяют **жирным** и используют в значении из этой страницы.
- Новый термин сопровождают кратким определением в разделе `Terms introduced`
  либо сразу добавляют сюда.
- Интервалы байтов задаются как полуоткрытые: `[start, end)`. `start` входит в
  интервал, `end` указывает на первый байт после него.
- Границы вызовов `recv` не считаются границами HTTP или иной прикладной
  структуры.
- Имена в коде должны следовать соглашениям Haskell, но сохранять понятия
  глоссария: например, тип `StructuralBoundary`, конструктор или значение
  `EarlyDecision`, поле `uriStart`.

## Поток и входные данные

### Byte Stream

Упорядоченная последовательность байтов, получаемая от клиентского соединения.
Proxy не предполагает, что границы чтения из сокета совпадают со структурными
границами HTTP-сообщения.

### Input Chunk

Одна физическая порция **Byte Stream**, возвращённая отдельной операцией чтения
из сокета. Это артефакт транспорта, а не прикладная структура. Один элемент
HTTP может пересекать несколько Input Chunk; один Input Chunk может содержать
несколько структурных элементов.

### Structural Boundary

Индекс в Byte Stream или в явно указанном буфере, зафиксированный парсером как
начало либо конец распознанного компонента запроса.

Примеры:

```text
methodStart
methodEnd
uriStart
uriEnd
headersEnd
bodyStart
```

Пара Structural Boundary образует полуоткрытый интервал `[start, end)` только
при условии, что обе координаты относятся к одной системе отсчёта.

## Сегменты локальной перезаписи

### Segment

Непрерывный диапазон байтов, рассматриваемый как одна единица пересылки.
Segment может ссылаться на существующую входную память без копирования, если
эта память остаётся живой до завершения отправки.

### Prefix

Неизменяемый Segment перед заменяемой областью. Для перезаписи URI:

```text
[requestStart, uriStart)
```

### Replacement

Новая последовательность байтов, заменяющая существующую область сообщения.
В первом эксперименте Replacement — результат перезаписи URI.

### Suffix

Неизменяемый Segment после заменяемой области. Для перезаписи URI в текущем
буфере:

```text
[uriEnd, currentlyBufferedEnd)
```

Suffix может включать заголовки и уже полученную часть тела запроса.

### Local Rewrite

Преобразование одной ограниченной области сообщения с сохранением окружающих
диапазонов байтов. Перезапись URI — первый эксперимент Local Rewrite.

Логическая форма результата:

```text
Prefix | Replacement | Suffix
```

### Message Reconstruction

Создание нового непрерывного буфера, содержащего полное преобразованное
сообщение. Для Local Rewrite это не стратегия по умолчанию: неизменённые
области не должны копироваться только ради получения единого буфера.

## Пересылка и момент решения

### Streaming Forwarding

Пересылка байтов backend-соединению по мере их доступности без обязательной
материализации полного запроса. Порядок и HTTP framing при этом должны
сохраняться.

### Early Decision

Решение о маршрутизации или авторизации, которое можно принять до полного
получения тела запроса. Например, backend может быть выбран по методу, URI и
заголовкам.

### Late Decision

Решение, зависящее от информации внутри тела запроса. До обнаружения нужного
признака Late Decision может требовать selective parsing и ограниченной
буферизации. Это не означает, что всё тело обязательно нужно материализовать.

### Passthrough

Пересылка диапазонов байтов без семантического преобразования. После Early
Decision и локальной перезаписи URI или заголовка последующие части тела обычно
могут перейти в режим Passthrough.

### Scatter/Gather I/O

Стратегия ввода-вывода, при которой несколько независимых сегментов памяти
передаются как один логический поток без предварительной конкатенации в единый
буфер. Это возможная последующая оптимизация; первая реализация может
использовать последовательные корректные отправки.

## Основные отношения

```text
Byte Stream
    └── delivered as Input Chunk(s)
            └── parser records Structural Boundary values

Local Rewrite
    └── Prefix | Replacement | Suffix
            └── Streaming Forwarding
                    ├── sequential sends
                    └── later: Scatter/Gather I/O

Decision
    ├── Early Decision → body may enter Passthrough
    └── Late Decision  → selective parsing / bounded buffering
```
