# stm-markov-proxy performance protocol

Этот документ задаёт воспроизводимую процедуру функциональных и нагрузочных
испытаний `stm-markov-proxy` на выделенном Linux-стенде.

Главное правило эксперимента:

> Сначала baseline. Затем одно изменение. Затем повторение тех же измерений.

Один удачный прогон является наблюдением, а не доказательством улучшения.

## Испытательный стенд

Измерения выполняются на выделенном Linux-стенде. Публичная документация не
фиксирует сетевое имя машины или реквизиты доступа. Существенные характеристики
окружения сохраняются в обезличенной карточке `machines/<host-id>.md`.

Инструменты устанавливаются без изменения системного окружения:

```text
$HOME/.ghcup       Haskell toolchain
$HOME/.local/bin   вспомогательные утилиты
```

Сборочные результаты Cabal остаются внутри репозитория в `dist-newstyle`.
На стенде уже доступен `wrk`. Версии всех инструментов фиксируются вместе с
результатами каждого прогона.

## Что хотим установить

Проект проверяет тезис:

> Универсальность принадлежит набору proxy-примитивов и механизму сборки, а
> runtime конкретного приложения должен содержать только выбранные компоненты.

Первый сравнительный эксперимент использует две сборки:

```text
Proxy Primitives + Application Model
                  |
                  +-- build A: основной proxy без optional output
                  |
                  `-- build B: основной proxy + optional output
                                              |
                                              +-- запись в файл
                                              `-- пересылка в сокет
```

Нужно проверить не только функциональную разницу, но и физическую цену
подключённой абстракции:

```text
выбранная компонента
        ↓
ветви и операции runtime
        ↓
аллокации / удерживаемая память / CPU
        ↓
latency / throughput / tail latency
```

Сборка без компоненты не должна исполнять её ветви, открывать её ресурсы или
нести её runtime-состояние.

## Порядок допуска к нагрузке

Нагрузочный тест не заменяет проверку корректности. Каждый вариант проходит
следующие ступени.

### 1. Чистые тесты автомата

Проверяем переходы на значениях вида:

```text
previous state + input chunk → next state / result
```

Минимальная матрица:

- поддерживаемые методы `GET`, `POST`, `PUT`;
- неизвестный и оборванный метод;
- пустой URI и URI у установленного предела;
- URI длиннее предела и ожидаемый отказ `414 URI Too Long`;
- request line и `CRLF CRLF`, разрезанные во всех существенных позициях;
- одинаковый логический запрос как один chunk, несколько chunks и поток
  однобайтовых chunks;
- правила Маркова, которые не применяются, применяются один раз и требуют
  возврата к началу колоды;
- malformed input и TCP EOF в каждой незавершённой фазе.

Найденный дефект сохраняется как regression test.

### 2. Живой функциональный тракт

Проверяем полный путь:

```text
client → proxy → backend → proxy → client
```

Для сборки с optional output дополнительно подтверждаем:

- точность записанных или пересланных байтов;
- порядок событий;
- поведение при недоступном файле или сокете;
- отсутствие output-побочных эффектов в сборке без компоненты.

### 3. Smoke-нагрузка

`wrk` используется для проверки живости и приблизительного предела текущего
тракта. Начальная форма команды:

```bash
wrk -t2 -c20 -d10s --latency http://127.0.0.1:8989/
```

Перед измерительной серией выполняется отдельный разогрев. Параметры команды
не меняются между сравниваемыми сборками.

### 4. Контролируемая серия

Vegeta используется для одинаковой заданной интенсивности и сохранения сырых
выборок latency. Инструмент устанавливается в
`$HOME/.local/bin`, когда этот этап станет необходим.

Для каждого варианта выполняется не менее трёх независимых измерительных
повторов после разогрева. Порядок вариантов чередуется, чтобы дрейф состояния
машины не совпал с одним вариантом сборки.

## Экспериментальные варианты

Первый полный цикл содержит как минимум:

| Вариант | Proxy | Optional output | Назначение |
|---|---|---|---|
| A | специализированный | отсутствует | baseline |
| B | тот же | запись в файл | цена file output |
| C | тот же | пересылка в сокет | цена socket output |

Между A, B и C нельзя одновременно менять parser, Markov rules, backend,
компилятор или параметры нагрузки.

Отдельные серии проводятся для:

- короткого обычного URI;
- URI около установленного предела;
- цельного входа;
- принудительно фрагментированного входа;
- успешного backend;
- контролируемой ошибки optional output.

## Что фиксировать

Для каждой серии сохраняются:

1. дата, commit SHA, ветка и чистота рабочего дерева;
2. ОС, архитектура и существенные сведения о машине;
3. версии GHC, Cabal, библиотек и генератора нагрузки;
4. флаги сборки и RTS;
5. точная команда, URI, длительность, threads, connections или rate;
6. конфигурация proxy, backend и optional output;
7. число запросов, req/s, объём передачи и ошибки;
8. latency average, standard deviation, maximum, p50, p75, p90 и p99;
9. CPU, максимальная резидентная память и RTS allocation metrics;
10. profiler output для отдельно выбранных диагностических прогонов;
11. сырые выборки, а не только итоговые агрегаты.

В сводную таблицу заносится медиана повторов и наблюдаемый разброс. До
накопления достаточной серии не вводится произвольный порог регрессии.

## RTS и profiling

Обычный измерительный бинарник и profiling-бинарник — разные инструменты.
Profiling не используется для утверждений об абсолютной производительности.

Для RTS-статистики фиксируется полный вывод запуска с `+RTS -s -RTS`. Для
поиска источника аллокаций выполняется отдельная profiling-сборка и отдельный
прогон при той же функциональной нагрузке.

Особенно проверяем гипотезы:

- стоимость побайтового роста строгого `ByteString` URI;
- удержание входных chunks срезами;
- аллокации состояния Вирта;
- отсутствие цены optional output в сборке A;
- цену записи в файл и цену пересылки в сокет по отдельности.

## Локальная структура результатов

Рекомендуемая структура, когда появятся первые данные:

```text
var/performance/
├── summary.csv
└── raw/
    └── YYYY-MM-DD/
        └── profile-id/
            └── run-NNN/
                ├── metadata.env
                ├── wrk.txt
                ├── rts.txt
                └── raw/
```

`doc/performance` в Sclerotix соответствует нашему `docs/performance`: здесь
живут протокол, обезличенные карточки машин и короткие датированные отчёты.
Сырые результаты остаются в `var/performance/` и в Git не добавляются.

## Критерий первого успеха

Первый эксперимент считается состоявшимся, когда:

- A, B и C получены из одной Application Model контролируемым выбором
  компоненты;
- функциональные тесты подтверждают различие поведения;
- сборка A не создаёт output-ресурсов и не выполняет output-ветвь;
- одинаковая нагрузочная серия воспроизводимо выполнена для всех вариантов;
- сохранены сырые данные, окружение и точные команды;
- наблюдаемое различие описано как эффект с разбросом, а не как одиночное
  красивое число;
- profiler или RTS metrics позволяют связать эффект с конкретной физической
  работой runtime.

До выполнения этих условий заявления «zero overhead», «компонента бесплатна»
или «вариант быстрее» остаются инженерными гипотезами.
