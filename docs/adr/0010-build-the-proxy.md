# ADR-0010: Build the proxy, don’t configure the proxy

## Статус

**ACCEPTED** (Принято)

## Контекст

Универсальный proxy runtime, поведение которого определяется большой динамической конфигурацией, переносит сложность в каждый запущенный экземпляр. При этом каждое приложение фактически использует только узкую часть возможностей.

Проекту нужна универсальность без универсального runtime: общие строительные блоки должны позволять получать разные, специфичные для приложений proxy-автоматы.

## Решение

Принимается принцип:

> **Build the proxy, don’t configure the proxy.**

Конкретный proxy automaton строится как результат специализации:

`Primitive Set + Application Model -> Specialized Application Proxy Automaton`

- `Primitive Set` содержит переиспользуемые proxy-примитивы: парсинг, маршрутизацию, авторизацию, трансформации, управление потоком и другие атомарные операции.
- `Application Model` описывает конкретное приложение: его правила, политики, операции, протокольные ожидания и допустимые переходы.
- `Specialization/Build Mechanism` валидирует модель, выбирает и компонует нужные примитивы и выпускает исполнимый автомат.

Универсальность живёт в наборе примитив и механизме сборки. Каждый собранный runtime остаётся узким, минимальным и application-specific. Он не должен содержать неиспользуемые ветви или динамически интерпретировать всю общую модель, если этого не требует конкретное приложение.

## Границы решения

- Это ADR закрепляет архитектурное направление, но не выбирает формат DSL, кодогенерацию, Template Haskell или иную технику специализации.
- Настройки развёртывания (адреса, секреты, лимиты ресурсов) могут оставаться runtime-конфигурацией. Принцип относится к функциональной форме и поведению proxy.

## Последствия

### Положительные

- меньше runtime-ветвлений, состояний и поверхности ошибок;
- явная трассируемость от application model к собранному автомату;
- возможность валидировать и оптимизировать конкретный автомат до запуска;
- независимое развитие primitive set и application models.

### Отрицательные

- нужны версионирование примитивов и воспроизводимые сборки;
- ошибки specialization mechanism могут влиять на все порождаемые proxy-автоматы;
- для каждой модели нужен отдельный build/test/deploy lifecycle.
