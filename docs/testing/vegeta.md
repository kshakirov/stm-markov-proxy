# Нагрузочная проверка с Vegeta

`vegeta` используется для подачи HTTP-нагрузки на локальный proxy и измерения
пропускной способности, задержек и доли успешных ответов.

## Проверка установки

```bash
vegeta --version
```

На рабочем Mac утилита установлена как `/usr/local/bin/vegeta`.

## Запуск proxy

Из корня проекта:

```bash
cabal run stm-markov-proxy
```

Текущая реализация открывает слушающий сокет на `127.0.0.1:8989`. Поле `port`
в `Config` пока не управляет фактическим портом.

Перед нагрузочным тестом полезно проверить один запрос:

```bash
curl -v http://127.0.0.1:8989/
```

## Короткая проверка

Сто запросов в секунду в течение 10 секунд:

```bash
echo "GET http://127.0.0.1:8989/" \
  | vegeta attack -rate=100 -duration=10s \
  | vegeta report
```

## Ступенчатая нагрузка

Сначала следует проверить умеренную нагрузку, а затем повышать частоту,
сохраняя одинаковую длительность каждого прогона:

```bash
echo "GET http://127.0.0.1:8989/" | vegeta attack -rate=100  -duration=30s | vegeta report
echo "GET http://127.0.0.1:8989/" | vegeta attack -rate=500  -duration=30s | vegeta report
echo "GET http://127.0.0.1:8989/" | vegeta attack -rate=1000 -duration=30s | vegeta report
```

Это три независимых запуска. Между ними нужно проверить, что proxy продолжает
работать и в терминале нет ошибок.

## Сохранение результата

Бинарный результат одного прогона:

```bash
echo "GET http://127.0.0.1:8989/" \
  | vegeta attack -rate=1000 -duration=30s \
  > results.bin
```

Текстовый отчёт:

```bash
vegeta report results.bin
```

Отчёт по интервалам задержки:

```bash
vegeta report -type='hist[0,1ms,2ms,5ms,10ms,25ms,50ms,100ms]' results.bin
```

HTML-график:

```bash
vegeta plot results.bin > results.html
```

Файлы результатов являются временными артефактами измерений. Перед добавлением
их в Git нужно отдельно решить, какие исходные результаты действительно нужны
для воспроизводимости эксперимента.

## На что смотреть

- `Success` — доля успешных HTTP-ответов;
- `Throughput` — фактически завершённые запросы в секунду;
- `Latencies` и перцентили `50th`, `95th`, `99th`;
- `Status Codes` — распределение кодов ответа;
- `Error Set` — сетевые и протокольные ошибки.

Высокий заданный `Rate` сам по себе не доказывает производительность proxy.
Сопоставлять нужно фактический `Throughput`, задержки, ошибки, загрузку CPU и
аллокации RTS.

## Текущее ограничение эксперимента

Текущий `handleClient` выполняет один `recv` размером до 1024 байт, отправляет
ответ и закрывает соединение. Поэтому эти команды пока проверяют сетевой каркас
и обработку короткого запроса, но не подтверждают корректность потоковой
обработки больших запросов или keep-alive.
